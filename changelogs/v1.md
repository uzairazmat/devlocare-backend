# Changelog — Version 1 (Phase 1: Backend Foundation + UC-01 Symptom Prediction)

---

## Portion 1 — Auth & Foundation

### What's New (For Everyone)

- **The app now connects to the database automatically when it starts.**
  When DevloCare starts up, it checks that it can reach the database. If the connection fails, the app refuses to start and tells you why — instead of silently breaking later.

- **Health Check page is live.**
  Visit `/api/v1/health` in your browser or any API tool. It will tell you `"status: healthy, db: connected"` if everything is working, or give a clear error if the database is down.

- **All actions are now logged with timestamps.**
  Every important event (startup, shutdown, DB connection, health checks, errors) is printed to the console with a time and label so you always know what the app is doing.

### What's Fixed (For Developers)

#### `app/core/logging.py` — NEW
- Created a single shared `get_logger()` factory used across all modules.
- Prevents duplicate log handlers being registered on hot-reload.
- Consistent log format: `YYYY-MM-DD HH:MM:SS | LEVEL | module | message`.

#### `app/db/session.py` — UPDATED
- `init_db()` now runs `SELECT 1` instead of just opening and immediately closing a connection — this actually verifies the DB responds.
- Added `logger.exception()` in `init_db()` so the full traceback is printed if the DB is unreachable at startup.
- `get_db()` now catches session-level exceptions, rolls back the transaction before re-raising — prevents dirty/hung transactions leaking across requests.

#### `app/api/v1/endpoints/health.py` — NEW
- Health check endpoint at `GET /api/v1/health`.
- Reuses the existing `get_db` dependency — no duplicate connection logic.
- Returns HTTP `503 Service Unavailable` with a human-readable message if the DB ping fails.

#### `app/api/v1/api_router.py` — NEW
- Central router with prefix `/api/v1`.
- All future endpoint routers (`predict`, `feedback`, etc.) will be registered here — `main.py` stays clean.

#### `app/main.py` — UPDATED
- Startup and shutdown events now log what is happening at each step.
- Removed inline DB connection check — delegates entirely to `init_db()`.
- Registers the central `api_router` in one line.

#### `app/db/models.py` — NEW
- SQLAlchemy ORM models for all 4 tables: `users`, `symptom_logs`, `disease_kb`, `feedback`.
- FK `ondelete` behaviours match the SQL schema (`SET NULL`, `CASCADE`).
- `CHECK` constraint on `feedback.rating` (1–5) mirrored from SQL.

#### `app/core/config.py` — NEW
- Reads all config from `.env` via `pydantic-settings`.
- Changing a connection string or secret only requires editing `.env` — no code changes.

#### Project Setup
- `requirements.txt` populated with all dependencies.
- `.env.example` added — safe template to commit, shows other devs what variables are needed.
- `.gitignore` covers `.env`, `venv/`, `.venv/`, `*.log`, `logs/`, `__pycache__/`, and IDE folders.

## Portion 2 — Symptom Prediction (UC-01)

### What's New (For Everyone)

- **Symptom prediction is now live at `POST /api/v1/predict/text`.**
  Send a 5–500 character symptom description and receive the Top-3 predicted conditions with confidence scores, a triage level (emergency / urgent / moderate / self-care), recommended specialist, bilingual care tips (English + Urdu), red flags and a medical disclaimer — all in one response.

- **Guests can use prediction without logging in.**
  Authentication is optional. Anonymous users still get a full prediction; their symptom log is saved with `user_id = NULL`. Logged-in users have their log attached to their account for history and feedback.

- **Privacy guard blocks personal information.**
  The endpoint rejects inputs that appear to contain an email, phone number, CNIC or card number before they are ever processed.

- **Intelligent triage engine personalises recommendations.**
  Triage level is raised automatically for emergency keywords (chest pain, stroke, anaphylaxis …), pregnancy + bleeding, patients under 5 or over 65 with moderate/severe symptoms, and users with declared chronic diseases.

- **Knowledge-base enrichment provides bilingual advice.**
  After prediction, the top condition is looked up in the `disease_kb` table to retrieve the specialist type, care tips in both English and Urdu, and red-flag warning signs.

- **All predictions are logged.**
  Every call creates a `symptom_logs` record that stores the raw text, Top-3 predictions, extracted symptoms, patient metadata, triage level and a `stub_mode` flag so teams can distinguish real-model predictions from development stubs.

### What's New (For Developers)

#### `app/clients/ml_client.py` — UPDATED
- `async predict_top_k(text, k=3)` loads `models/model.pkl` lazily via `joblib` (thread-safe, single load).
- Supports three artefact layouts: full sklearn `Pipeline`, `{"vectorizer", "model"}` bundle, or bare classifier + separate `vectorizer.pkl`.
- Runs the sklearn call in `asyncio.to_thread` so the FastAPI event loop is never blocked.
- Falls back to a deterministic rule-based stub when no model file is present; stub is clearly labelled in every response (`stub_mode: true` in `explanation_json`).

#### `app/services/preprocess_service.py` — NEW
- `clean_text(text)` — lowercase, tokenize with regex, remove English stopwords (NLTK with built-in fallback list when NLTK is not installed).
- `extract_symptoms(text)` — spaCy `Matcher` over a 20-entry symptom lexicon (fever, cough, rash, headache, chest pain, shortness of breath, …); regex fallback when spaCy is unavailable.
- `vectorize_text(text)` — loads `models/vectorizer.pkl` and returns a sparse matrix; returns `None` if no standalone vectorizer is present (full Pipeline handles it internally).
- All NLP resources are loaded lazily and cached; missing libraries degrade gracefully rather than 500ing.

#### `app/services/prediction_service.py` — UPDATED
- Main orchestrator following the 9-step project flow.
- Calls preprocess → extract_symptoms → vectorize → ml_client → triage → kb_lookup → persist → return.
- `_compute_triage()` applies an ordered rule engine: emergency keywords > pregnancy flags > KB-declared category > urgent keywords + severity > age extremes > chronic disease > `self-care`.

#### `app/services/kb_service.py` — UPDATED
- `lookup_disease(db, condition_name)` — exact (case-insensitive) match on `name_en` first; falls back to partial `LIKE` on both `name_en` and `name_ur`.

#### `app/repositories/log_repo.py` — UPDATED
- `create(db, log)` and `get_by_id(db, log_id)` for the `symptom_logs` table.

#### `app/models/request.py` — UPDATED
- `SymptomTextRequest` added — `text` (5–500 chars, PII-blocked), plus optional `age`, `sex`, `duration`, `severity`, `pregnancy`, `chronic_disease`.

#### `app/models/response.py` — UPDATED

#### `app/api/v1/deps.py` — UPDATED

## Portion 3 — History & PDF Export (UC-06)

### What's New (For Everyone)

- **Saved consultation sidebar.**
  Registered users now have a ChatGPT-style left sidebar listing every consultation they've made. Hit `GET /api/v1/history?limit=15&offset=0` to retrieve a page; the response includes a `has_more` flag and a `total` count so a "Load more" button can paginate older entries cleanly. Guests receive an empty list with the friendly message `"Login to save and view your consultation history"`.

- **Delete on demand.**
  `DELETE /api/v1/history/{log_id}` permanently removes a consultation. The endpoint is owner-locked: trying to delete someone else's log returns `404` (we deliberately don't distinguish "not yours" from "not found" to avoid leaking the existence of foreign IDs). Every successful delete is recorded with an `AUDIT history.delete` line in the application log.

- **Download a professional PDF report.**
  `POST /api/v1/history/export` produces a clean A4 medical consultation PDF that any browser can save with one click. The body accepts either an explicit `{"log_ids": [...]}` selection or `{"last_n": N}` for the most recent consultations (1–50). Each page contains the date, the original symptom description, top-3 predictions with confidence percentages, the AI rationale + key symptoms + feature importance + recommendation, patient metadata, the triage level (colour-coded), and the standard medical disclaimer. The footer carries page numbers and the DevloCare brand line.

- **No re-running the model on export.**
  Every prediction call already persists the full Top-3 + explanation bundle inside `symptom_logs.explanation_json`, so history retrieval and PDF generation are pure read operations. Exports are deterministic and instant.

### What's New (For Developers)

#### `app/repositories/log_repo.py` — UPDATED
- `get_user_history(db, *, user_id, limit, offset)` returns `(items, total)` for the sidebar — efficient SQL paging, ordered `created_at DESC`, plus a separate `COUNT(*)` for `has_more`.
- `delete_log(db, *, log_id, user_id)` issues an ownership-scoped `DELETE` and returns the affected row count, so the caller can map `0` to a 404.
- `get_logs_for_export(db, *, user_id, log_ids=None, last_n=None)` supports both selection modes, silently filtering out IDs that don't belong to the caller (no info leakage).

#### `app/services/pdf_service.py` — NEW
- ReportLab Platypus-based PDF builder (`build_history_pdf`).
- Pure function — takes a list of `SymptomLog` rows and returns `bytes`; never queries the DB and never re-runs ML inference.
- Robust against missing/malformed `explanation_json` (older logs, stub-mode logs).
- Triage colour badges (green = `self_care`, amber = `see_gp`, red = `urgent_care`), summary tables, page chrome with brand line + page numbers, English medical disclaimer at the end.
- All user-supplied strings are HTML-escaped before being passed to ReportLab paragraphs to keep markup safe.

#### `app/api/v1/endpoints/history.py` — NEW
- `GET /api/v1/history` — paginated sidebar list, guest-aware.
- `DELETE /api/v1/history/{log_id}` — single delete with ownership guard and audit log line.
- `POST /api/v1/history/export` — returns `application/pdf` with `Content-Disposition: attachment; filename="devlocare-consultations-<user>-<timestamp>.pdf"` so browsers download immediately.
- `Cache-Control: no-store` set on exports to keep medical data out of intermediate caches.

#### `app/models/request.py` — UPDATED
- `HistoryExportRequest` added — exactly one of `log_ids` (max 50, deduped, positive integers) or `last_n` (1–50) must be supplied; helper `resolved_mode()` raises a clear validation error if both or neither are provided.

#### `app/models/response.py` — UPDATED

#### `app/api/v1/api_router.py` — UPDATED

## Portion 4 — Feedback Loop (UC-08)

### What's New (For Everyone)

- **Rate any consultation 1–5 with an optional comment.**
  Authenticated users can now submit a helpfulness rating (1–5) and an optional free-text comment for any of their saved consultations via `POST /api/v1/feedback`. The frontend's thumbs / rating popup that appears after a diagnosis can call this endpoint directly. Re-submitting feedback for the same consultation **updates** the existing rating instead of creating duplicates — the database enforces one feedback row per `(log_id, user_id)` pair via a unique constraint, so spam is structurally impossible.

- **Owner-only feedback.**
  A user can only leave feedback on their *own* consultations. Trying to rate someone else's `log_id` returns `404` (we deliberately don't distinguish "not yours" from "not found" to avoid leaking foreign IDs). Every successful submit / update is recorded as an `AUDIT feedback.create` or `AUDIT feedback.update` line in the application log.

- **Strict input validation.**
  `helpfulness_rating` is rejected with a 422 if it's not an integer between 1 and 5. `feedback_text` is trimmed of whitespace, capped at 1000 characters, and blank strings are normalised to `null` so the database never stores noise.

- **Lightweight model-monitoring endpoint.**
  `GET /api/v1/feedback/monitor` returns a single aggregated JSON payload designed for an admin / QA dashboard or a scheduled report. In one round-trip you get: total feedback count, the running average rating, the full 1–5 distribution, the count of low ratings (≤ 2), the most recent low-rated consultations (with their predicted condition + triage level), the most recent negative free-text comments, and breakdowns of count + average rating by triage level and by predicted condition. Everything is computed via SQL aggregation so the endpoint stays cheap as the table grows. A clearly-marked `# NOTE` reserves the spot where a future admin/staff role guard will plug in once a role system exists.

### What's New (For Developers)

#### `app/db/models.py` — UPDATED
- New `ConsultationFeedback` model backing the dedicated `consultation_feedback` table — completely separate from `symptom_logs` so that table is never polluted with feedback columns.
- Columns: `feedback_id` (PK), `log_id` (FK → `symptom_logs.log_id`, `ON DELETE CASCADE`), `user_id` (FK → `users.user_id`, `ON DELETE CASCADE`), `helpfulness_rating` (NOT NULL, `CHECK 1 ≤ rating ≤ 5`), `feedback_text` (nullable), `created_at`, `updated_at`.
- `UniqueConstraint(log_id, user_id)` enforces one feedback per (consultation, user) pair at the DB layer.
- Indexes on `log_id`, `user_id`, and `helpfulness_rating` keep monitoring queries fast.
- The legacy placeholder `Feedback` model has been retired in favour of this purpose-built table.

#### `app/repositories/feedback_repo.py` — NEW
- `get_by_log_and_user(...)` — point lookup used to decide insert vs update.
- `create_or_update_feedback(...)` — idempotent upsert that respects the unique constraint and returns `(row, created)` so the API layer can emit the right audit line / response message.
- `get_feedback_monitoring_stats(...)` — computes every field of the monitor payload via pure SQL aggregation: headline counters in one `COUNT/AVG/SUM(CASE WHEN…)` pass, the rating distribution via `GROUP BY rating` (every 1–5 bucket is always present, defaulting to 0), recent low-rated cases joined to `symptom_logs` for context, top negative comments filtered to non-blank text, and breakdowns by `triage_level` and `predicted_condition`.

#### `app/api/v1/endpoints/feedback.py` — NEW
- `POST /api/v1/feedback` — submit / update feedback. JWT-required. Ownership is enforced before any write by re-fetching the target log and checking `user_id`; foreign / missing logs get a 404. Returns `FeedbackSubmitResponse` (a `message` + the stored `FeedbackResponse` object) so the frontend can show a toast and update local state in one shot.
- `GET /api/v1/feedback/monitor` — JWT-required for now, with an inline `# NOTE` documenting where to add a `require_admin` dependency once roles exist. Logs an `AUDIT feedback.monitor` line on every access so admin-only access is traceable retroactively.

#### `app/models/request.py` — UPDATED
- `FeedbackCreateRequest` added — `log_id` (positive int), `helpfulness_rating` (1–5 strict), `feedback_text` (nullable, ≤ 1000 chars, trimmed, blank-normalised to `None`).
- `FEEDBACK_TEXT_MAX_LENGTH` constant exported so frontend / tests can import the same limit.

#### `app/models/response.py` — UPDATED
- `FeedbackResponse` (single feedback row, `from_attributes=True`), `FeedbackSubmitResponse` (`{message, feedback}` envelope) and `FeedbackMonitorResponse` (full aggregate payload with typed sub-models for each list section) added.

#### `app/api/v1/api_router.py` — UPDATED
- Feedback router registered under `/api/v1/feedback`.
